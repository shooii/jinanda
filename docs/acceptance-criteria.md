# 验收标准与指标清单

> 用途：作为外包开发合同的**附件一**。每一条都可单独引用，例如「不满足 A-4 的通过条件，判定为 P1 缺陷」。
> 甲方＝委托方，乙方＝承接开发方。文档中所有条款均为**验收条件**，不含建议。

## 0. 通用约定

### 0.1 验收环境

1. 所有功能验收在**甲方提供的干净环境**进行：甲方自有机器与设备、甲方账号、从乙方交付的仓库从零构建。
2. 硬件相关功能（蓝牙连接、电量、固件、降噪、手势、双耳音频）**必须在真机 + 真耳机上验证**，模拟数据一律不计入通过。
3. 每次验收留存环境信息：机型、系统版本、App 版本 / 构建号、耳机型号与固件版本、网络条件。

### 0.2 证据形式

每个验收项的通过证据必须是以下之一，且**甲方环境可复现**：

| 证据类型 | 要求 |
| --- | --- |
| 录屏 | 包含完整操作路径与时间戳，不能剪辑 |
| 截图 | 包含关键状态与错误态，不接受只有成功态 |
| 日志 | 原始日志文件（崩溃、网络、蓝牙事件） |
| 自动化结果 | 原始测试报告文件（JUnit / HTML），不接受口头结论 |
| 性能原始数据 | 采集工具导出的原始数据（含 P50/P95、设备与网络条件） |
| 第三方报告 | 检测机构、商店审核、安全扫描的原始报告 |

**不接受**：只有结论的 PPT、无法复现的演示视频、只在乙方环境可运行的构建。

### 0.3 缺陷分级

| 级别 | 定义 | 修复期限 |
| --- | --- | --- |
| P0 | 崩溃、数据丢失、隐私泄露、无法启动、主流程完全不可用 | 24 小时内 |
| P1 | 核心功能不可用且无绕过方式；能力声明与实际不符 | 3 个自然日 |
| P2 | 功能可用但体验明显缺陷、局部机型不兼容 | 2 周 |
| P3 | 优化建议、文案与视觉细节 | 双方协商 |

### 0.4 阶段与付款

| 阶段 | 出口条件 | 付款比例 |
| --- | --- | --- |
| α 功能可用 | A–H 模块功能验收通过，P0/P1 缺陷为 0 | 20% |
| β 可测 | 第 3、5 章工程质量与兼容性验收通过 | 20% |
| RC 可发布 | 第 4、6、7、8 章通过，第 9 章上架材料齐备 | 20% |
| 上线 | 通过商店审核并正式发布 | 20% |
| 终验 | 试运行（第 12 章）结束，交付物移交完成 | 20% |

## 3. 性能与稳定性指标

以下为**建议阈值**，实际数值须结合第 13 章的当前基线协商确定。测试条件：中端安卓真机、4G、冷启动、连续 3 轮取中位。

| 编号 | 指标 | 建议阈值 |
| --- | --- | --- |
| P-1 | 冷启动到可交互 | P50 ≤2.0s，P95 ≤3.5s |
| P-2 | 首屏内容渲染 | P95 ≤2.5s |
| P-3 | 崩溃率 | <0.5%（按会话） |
| P-4 | ANR / 无响应率 | <0.1% |
| P-5 | 翻译端到端延迟 | P50 ≤800ms，P95 ≤1.5s |
| P-6 | 蓝牙连接成功率 | ≥98%；断连自动恢复 ≤10s |
| P-7 | 离线可用率 | 已下载语言包场景 100% |
| P-8 | 内存峰值 | 双方约定上限，且连续使用 30 分钟无增长趋势 |
| P-9 | 后台耗电 | 后台 1 小时耗电 ≤ 双方约定值 |
| P-10 | 首包体积 | 主包 gzip ≤ 约定值 |
| P-11 | 长时间稳定性 | 连续 2 小时会话无崩溃、无内存泄漏引发的卡顿 |

## 4. 兼容性验收矩阵

至少覆盖下表；每个机型均需跑通 A/B/C/D 四组 P0 用例并记录结果。

| 维度 | 要求 |
| --- | --- |
| iOS | 最近 3 个大版本（当前为 16 / 17 / 18），含 1 台老机型 |
| Android | 12 / 13 / 14 / 15，含 1 台低端机（≤4GB 内存） |
| 厂商 | 华为、小米、OPPO、vivo、三星各至少 1 台 |
| 平板 / 折叠屏 | 至少 1 台，验证布局不破版 |
| 浏览器 / WebView | 若交付含 PWA 或 WebView，需列明支持矩阵 |
| 能力受限机型 | 逐项列明哪些能力不可用、降级后的界面文案 |

**能力差异必须显式交付**：端侧翻译 / 识别模型、蓝牙直连、后台播放等能力在不同平台差异很大，乙方必须提交「能力矩阵表」，并在应用内如实提示，不允许用户自行发现。

## 9. 反模拟专项检查（现场执行，发现即判 P1）

以下检查用于识别「用模拟顶替真实现」的做法，全部由甲方现场操作：

1. 拔掉真耳机 → 电量 / 型号 / 固件是否变为「未知」，而不是继续显示数字
2. 断网 → 依赖网络的功能是否明确失败提示；本地功能是否真能用
3. 拒绝权限 → 是否给出可执行引导，而不是崩溃或空白页
4. 点击「检查更新」「刷新」「同步」类按钮 → 背后是否有真实数据源
5. 切换界面语言 → 是否仍有原语言残留
6. 清空数据 / 重装 → 是否出现示例假数据伪装成已有内容
7. 抓包 → 「云端校验」「同步」是否真的打到服务端
8. 注入错误 → 是否真的上报到监控平台

## 11. 验收流程与节点

1. **乙方自测**：提交《自测报告》+ CI 结果 + 《已知问题清单》（隐瞒已知问题视为重大违约）
2. **甲方复现**：干净环境从零构建，跑完 P0 用例，抽测 ≥30% 的 P1 用例
3. **专项验收**：性能、兼容性、无障碍、安全隐私、国际化五份专项报告，各自负责人签字
4. **试运行**：真实用户内测 2–4 周，采集崩溃率、翻译质量、留存与反馈，形成《试运行报告》
5. **终验**：缺陷清零 + 交付物移交完成 + 验收报告签字 → 支付尾款
