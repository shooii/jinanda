# 交付物清单与移交确认表

> 用途：作为外包开发合同的**附件二**，与《验收标准与指标清单》配套使用。
> 原则：**拿不到 = 没交付；只有乙方能跑通 = 没交付；没有书面确认 = 没交付。**

## 0. 交付原则

1. **可复现**：甲方在自有干净环境按交付文档完成安装、构建、运行，不需要乙方协助。
2. **可维护**：甲方自有或新聘团队能够在不联系乙方的前提下修改功能、修复缺陷、发版。
3. **可转移**：账号、密钥、证书、云资源的所有权与管理权转移到甲方。
4. **无隐藏依赖**：不得依赖乙方私有仓库、私有构建服务、个人账号、未文档化的手工步骤。
5. **交付即冻结**：每次交付对应一个 Git tag 与构建号，交付后任何改动须走变更流程并重新验收。

## 2. 代码与版本控制（重点核对）

- [ ] 仓库所有权归甲方；乙方人员权限在移交后调整或移除
- [ ] 提交历史完整，无「压缩成一个 initial commit」的情况
- [ ] 存在分支策略与提交规范说明（主干保护、评审规则）
- [ ] 无子模块 / 私有包 / 私有源指向乙方内部资源；如存在，须一并移交或移除
- [ ] 大文件与二进制资产有明确的存储方式（如 LFS），甲方可完整拉取
- [ ] 仓库中无密钥、证书私钥、token、个人账号信息（提供全库扫描结果）
- [ ] 代码中包含的绝对路径、环境相关硬编码已清理
- [ ] 提供「从零构建」的可执行步骤，且已在甲方环境验证通过

---

## 3. 构建、签名与发布

- [ ] 流水线可在甲方账号下运行（CI 检查项、构建、产物上传）
- [ ] 版本号规则明确（含构建号 / 渠道号），可追溯到 Git tag
- [ ] 各环境（开发 / 测试 / 生产）配置分离，密钥通过环境变量或密钥管理服务注入
- [ ] 提供一次完整的发布演练记录：打包 → 上传 → 审核提交 → 灰度 → 回滚
- [ ] 回滚方案经过实际演练（不是纸面方案）

---

## 4. 技术文档（验收时逐份提问答辩）

文档的最低要求是可以让一个**没有参与开发**的工程师据此接手。参照本仓库现有文档的形式：

- [ ] 架构说明：模块划分、状态管理、数据流、错误处理与降级策略
- [ ] 接口契约：参照 `docs/api-contract.md` 的粒度，含鉴权、幂等、错误体、约定与未完成项
- [ ] 硬件对接：参照 `docs/hardware-bridge.md`，**必须明确区分「已实现」与「需原生能力」**，并写明限制原因
- [ ] 运维手册：部署、配置、监控指标、告警阈值、常见故障处置
- [ ] 已知问题清单：影响面、触发条件、规避方式、计划修复版本

## 5. 测试资产

- [ ] 测试用例库可读、可执行，覆盖功能 / 兼容 / 异常三类
