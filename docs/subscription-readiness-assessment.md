# LingoPods 美欧订阅系统就绪度评估

评估日期：2026-10-21
范围：以美国及欧洲消费者为主要市场的 LingoPods 订阅产品。本文依据仓库内 `docs/business-model.md`、`docs/global-payments-design.md`、`docs/api-contract.md`、`docs/acceptance-criteria.md`、`docs/deliverables-handover.md`；不是法律意见，也不把方案文档中的设想视为已上线能力。

## 结论摘要

当前有成形的套餐与权益方案、客户端付费墙/用量逻辑和服务端接口草案；但文档明确后端尚未接入，未配置 API 时权益校验失败并进入本地模式。支付渠道、商店收据验证、webhook、交易恢复/对账和退款链路不能视为已上线。目标若包含 iOS/Android 原生商店分发，还需要原生购买能力；当前交付基线是 PWA。

**上线判断：**可继续做产品验证，但在真实收费开放前，必须完成真实渠道交易、服务端账本与权益状态机、价格/税务核验、取消退款和恢复流程，以及目标地区法律审查。若仍以 PWA 发布，商店 IAP/Play Billing 章节不适用，但不能把 PWA 伪装成已支持商店购买；若上架原生包，需按对应商店 storefront、分发方式及最新条款重新核验。

证据分级：**资料确认**表示仓库文档明示；**代码需核验**表示文档给出实现描述但本次没有逐文件审计代码；**缺失/待接**只在资料明示未完成时使用。文档中的政策/费率数字属于设计文档陈述，不作为本评估的权威法律结论。

## 功能缺口

### 已有或已设计（不代表生产可用）

- **资料确认：**三档 Free/Plus/Pro 权益、月/年价格、7 天 Pro 试用、试用结束处理、到期降级不锁设备及附加一次性商品见 `business-model.md`。
- **资料确认：**客户端用量、付费墙和会员页被文档描述为已有；使用量本地保存在 `localStorage`，正式环境要求改服务端计量。
- **资料确认：**账号认证、权益校验、同步接口契约已定义；未配置服务地址时进入本地模式，权益校验失败，后端尚未部署。详见 `api-contract.md` 第 3、69-87 行。
- **资料确认：**收据验证契约涵盖 Apple/Google/部分 Android 厂商/Stripe/PayPal，但其本身不是各渠道 SDK、商户账户、回调或生产验证实现。
- **资料确认：**`global-payments-design.md` 明示当前支付流程含模拟 720ms 步骤；PWA 不含 StoreKit/Play Billing，列出的商店渠道为演示态。
- **待接/上线阻断：**生产商品目录与价格报价服务、真实结账、渠道回调/通知、服务端订阅账本、取消/暂停/续订、拒付退款同步和客服后台。具体可售渠道取决于发行形态。
- **待接/上线阻断：**可恢复购买、换机/重装后重新对账、网页购买跨设备授权、账号解绑/合并冲突处理。验收标准 E-4 已要求恢复购买，但 API 契约未定义恢复端点与完整映射流程。
- **待补：**当前 `Entitlement` 示例仅有 `source/planId/expiresAt/verified`；缺少明确的订阅 ID、商店交易/原始交易 ID、用户绑定、SKU、周期、续费状态、取消生效时间、试用时间、宽限期、退款撤销、税额、币种、地区与事件版本等持久化字段。
- **待补：**只按客户端 `id` 幂等不足够；需对平台交易 ID、webhook 事件 ID、事件序列和重复/迟到通知分别防重、排序与重放。
- **待补：**支付失败状态告知、更新支付方式、重试与宽限策略、到期预告、试用结束通知、账单/发票、取消和退款入口、投诉及申诉路径。
- **待核验：**终端取消后是否能实时同步到服务器；已取消但本期仍有效、退款后立即撤权、拒付冻结、撤销后恢复、重复购买补偿等边界行为尚未形成可验收规则。

### 主要风险

1. **收钱却不开权/重复收款：**客户端支付成功但服务端未确认；超时重试造成重复订单；迟到通知覆盖较新状态。
2. **权益错误或被滥用：**客户端可信、本地用量可改、收据重放、一个交易绑定多个账号、同账号多渠道重复订阅。
3. **平台拒审/条款违规：**把网页支付放进商店包而不满足例外条件，或把实体/数字商品支付路径混用。
4. **税价/退款损失：**动态汇率变价、税额未计入展示、跨区地址误判、错误使用退款窗口或税务主体不匹配。
5. **消费者伤害与声誉损失：**试用转付费不清晰、取消困难、退款后仍扣费、到期把耳机核心功能锁死。
6. **设备兼容性被混为平台差异：**把 iOS/Android、App Store/Play/PWA、Samsung/Xiaomi/OPPO 品牌差异压成一个 `platform`，会误导支付能力和硬件支持声明。

## 订阅系统需求

以下按“真实收费前必须”定义；权益回落必须保证基本翻译和已产生数据可用，不因订阅到期把硬件变砖。

### 1. 商品、套餐、定价

- 建立服务端商品目录：稳定 `skuId`、权益集合、计费周期、商店产品 ID 映射、上架地区/渠道、可售状态、税务类别、价格版本和生效时间。
- 先签批首发 SKU；建议首发只启用已验证的订阅档位与周期。Lifetime、消耗包、实物配件分别有明确的 entitlement/余额/物流模型，避免混为 subscription。
- 价格由对应商店/支付渠道或服务端 price book 提供，客户端不得用 FX/PPP 即时换算生产售价。报价应锁定金额、币种、含税状态、税额/总额、周期、试用条件、首扣日期和有效期。
- 价格变化必须按国家、渠道与合同版本配置；对存量用户按适用规则预通知并记录同意/接受状态，不得静默改价。
- 结账确认页必须清楚展示当前应付金额、续费金额和频率、自动续费、试用何时结束/首次扣款、取消方式、税额是否已含及条款/隐私链接。无试用也需明确首次收费。

### 2. 生命周期与权益状态

- 统一状态至少支持 `none/trialing/active/canceled_at_period_end/past_due/grace/paused/expired/refunded/revoked/chargeback`；用有效期、自动续费状态、宽限起止与来源事件表达，不以单一 `verified` 布尔值替代。
- 明确试用政策：账号级/商店级限制、资格校验、是否要先授权付款方式、是否自动转付费、结束提醒时间与渠道、试用取消立即还是期末失效。商店商品配置与前端描述必须一致。
- 升级/降级按渠道支持能力实现：升级即时生效或按比例计费/结算；降级应说明下周期生效及当前周期权益。App Store/Play 的 prorations、同组订阅和变更规则不可由通用网页模型臆造，逐渠道验收。
- 取消默认停止下次续费而保留已付周期权益；提供平台管理订阅入口或 PSP 门户。不得把“取消意向”当作立即撤权。暂停仅在该渠道支持且产品确认后开放。
- 扣款失败：展示失败原因（不过度泄露）、更新时间和重试状态；接收渠道的 billing retry/grace 信号。宽限期长度由渠道能力与商业政策明确配置，失败最终到期则降级 Free；不可假设所有商店都能自定义同一宽限策略。
- 退款/撤销/拒付须由渠道通知或定期对账驱动；定义即时撤权、部分退款、消耗型余额扣回/负余额、争议中临时权益以及误撤销申诉/恢复流程。依法或依渠道须退款的流程不能被“不可退款”文案覆盖。

### 3. 账号绑定、恢复、跨设备

- 收据/购买令牌服务端校验后绑定至已认证 `userId`，记录 `storeAccountToken/appAccountToken` 等平台关联标识（按平台能力与隐私审查）；客户端传入的账户 ID 不能成为可信依据。
- 服务端权益为账号级单一投影；设备登录后同步，客户端仅展示缓存。每次登录、恢复购买、交易通知及关键权益请求触发 reconcile。
- 购买前登录或在购买后建立确定的账号绑定流程；同一 Apple/Google 账户购买被多个 App 账号恢复时，给出明确冲突处理，不可静默转移/重复发权益。支持用户证明所有权后的账号迁移审计流程。
- 设置/会员页提供“恢复购买”和“管理订阅”，恢复要显示进行中、成功、无记录、不同商店账户、网络失败和需登录账号等结果；恢复必须再次向服务端校验并做权益对账。
- 设计跨平台策略：若同一产品允许网页/商店并行购买，如何避免重复订阅；若商店政策限制商店版购买方式，应明确界面引导边界。商店权益能否在网页/其他平台消费需要逐平台核实，不默认可跨平台使用。

### 4. 交易可靠性与运营

- 服务端维护订单、订阅、交易、权益授予、退款、税款及事件日志；敏感支付凭证交由合规 PSP/商店托管，避免自行保存卡号。
- Webhook/服务器通知须验证签名、幂等、持久化后异步处理，支持重复、乱序、延迟、撤销及重放；关键事件补主动查询平台 API 和定期对账。
- 订单链路需有状态机、超时与补偿：`created/pending/paid/failed/refunded/chargeback`；用户支付但回调延迟要可自助刷新，不重复发起新付款。
- 运营后台至少能按订单/用户/交易 ID 查询、重试验证、重放事件、查看权益变化、标注人工退款与审计操作；客服只能按角色授权。
- 客户端幂等键适用于请求重试，但交易唯一性必须以商店/PSP稳定交易 ID 为准；账号、原始订阅 ID、商品和平台组合应有唯一约束与异常告警。
- 记录自动续费明示同意版本、展示内容、时间、locale、报价/价格版本及来源；限权访问并设置保留期。删除账号不得抹掉依法/支付争议所需账务记录，但需去标识化并向用户说明。

### 5. 必备测试与观测

- Sandbox/测试环境端到端：成功、用户取消、待处理、重复回调、验证失败、退款、拒付、取消后期末权益、续订、升级降级、试用转换、扣款失败/宽限、恢复、换机、账号冲突、离线与回调延迟。
- 按渠道和国家分别验证价格、币种、税显示、收据、发票、取消入口和退款入口；测试账号不得产生真实扣款。
- 指标：结账成功率/失败码、回调延迟与丢失、恢复成功率、重复订阅率、past_due 恢复率、退款/拒付率、状态对账差异及权益错发数。设置交易未授权、事件积压、价格错配、退款未撤权告警。

## 平台与地区差异

### 操作系统、分发渠道、厂商品牌必须分开

| 维度 | 主要影响 | 对 LingoPods 的设计要求 |
|---|---|---|
| 操作系统/设备能力 | BLE、通知、后台运行、支付 API 可用性、UI 能力 | 能力探测与真机验证；iOS/iPadOS 与 Android 不共用未经验证的功能假设。 |
| 分发/支付渠道 | IAP/Play Billing/网页 PSP、退款来源、收据格式、通知机制、佣金和审核 | 权益数据保留 `storefront + distributionChannel + paymentProvider`；政策规则以渠道/地区配置，不单看 OS。 |
| 厂商品牌/ROM | 后台限制、推送、BLE 兼容、应用市场审核及支付服务覆盖 | Samsung、Xiaomi、OPPO 等只有在实际上架对应商店、签约并完成 SDK/服务端验证后才是可用支付渠道；品牌设备不等于该品牌商店购买。 |

### Apple / iOS

- **原生 App Store 包：**数字订阅功能通常需遵循 App Store IAP 规则；商品、试用和周期需配置在 App Store Connect。恢复可恢复购买、显示订阅信息及提供管理路径应纳入验收。实体商品与数字订阅适用不同支付规则。
- **iOS 设备上的网页/PWA：**不自动等同 App Store 包；采用网页 PSP 不代表可在原生 App 内自由引导外付。审核适用性取决于是否为商店包、所在 storefront、当前例外计划和条款。
- **外链/替代支付：**美国与欧盟规则在诉讼、监管及 Apple 商业条款变化期间可能调整；佣金、资格、披露、链接 entitlement、报告义务及生效日期全部列为上线前核实，不采用 `global-payments-design.md` 中“Apple 外链 0%”等数字作为商业决策依据。
- **设备兼容另议：**当前资料描述使用 Web Bluetooth；iOS Safari 能否连接耳机及原生壳方案是产品核心阻断，不是订阅规则。支付上线前须先明确 App Store 原生壳与 BLE 的交付边界。

### Android 与 Google Play

- **Google Play 分发包：**数字功能/订阅通常使用 Play Billing；订阅商品、base plan、offer、地区可售设置在 Play Console 配置。需按当前 Play Billing 库和 API 要求进行服务端验证、通知及 acknowledgement/确认时限处理。
- **替代计费/外部链接：**仅在符合适用地区、项目注册与报告要求时使用；收费和用户体验不得依据旧费率或博客，需在 Play Console 和官方政策逐市场确认。
- **Android 不等于 Google Play：**侧载、OEM 商店、预装渠道及浏览器分发可能有不同账单要求和可用 SDK；按具体发行渠道建能力矩阵。

### 美国

- 价格显示、自动续订、免费试用、取消与退款涉及联邦 ROSCA/FTC 执法、州级自动续费法、支付网络规则及各商店合同，适用范围和生效文本需美国律师按实际销售州及购买路径核验。
- 账单地址、税务 nexus、州/地方销售税、经济关联门槛和数字服务税务分类需由税务顾问及 MoR/PSP确认；不能以 IP、语言或单一“美国税率”代替。
- 隐私需按实际覆盖州审查（例如加州州法）及适用联邦/行业规则；明确音频、转写、设备标识、订阅/账单数据的用途、共享、删除和选择退出。未成年用户覆盖范围必须先确认。
- Visa/Mastercard 的试用提醒与订阅指引是支付网络合同要求，不等同所有州法；由收单方提供当前书面规则和例外条件。

### 欧洲（欧盟/EEA 与英国分别处理）

- 欧盟消费者权利、数字服务/内容撤回权、续费/取消和价格展示应按订阅合同结构、立即提供服务的用户同意、成员国实施法分别审查。不要把“所有订阅一律 14 天全额退款”或“签字即可完全放弃撤回权”写成全欧通则。
- VAT OSS/IOSS 适用取决于供货性质、卖方/商户主体及交易链路；电子服务 B2C 税率通常关联消费者所在地，但税务义务、含税定价、发票和记录要求需按目标国与 MoR 模式核验。
- GDPR/ePrivacy：确定控制者/处理者、合法基础、最小化、保留删除、数据主体权利、供应商 DPA、跨境传输机制及必要的 DPIA；营销同意与服务通知分开。音频/会议数据需评估敏感性和录音同意要求。
- SCA/PSD2 适用和周期性扣款豁免由 PSP/收单行按交易场景判断；支付系统应支持 3DS/SCA challenge 与失败恢复，不应一概承诺所有续费都免验证。
- **英国单列：**UK GDPR、消费者和订阅法、VAT 与支付渠道资格分别核验，不能直接套用欧盟法规结论。
- 欧盟成员国、EEA 非欧盟国家、英国、瑞士的币种和税务不完全相同。至少以实际上市国家建价格/税务/语言矩阵；英文界面覆盖不代表法律披露本地化已满足。

## 上线优先级

### P0：任何真实收费开放前必须完成

1. 确认分发形态、首发国家/渠道、商业主体、MoR/PSP 与 SKU；冻结渠道政策假设并获得法务/税务书面复核。
2. 服务端商品/价格目录与实际收款渠道打通；真实沙盒/测试交易端到端可完成，价格、币种、税费和续费条款匹配。
3. 服务端交易账本、用户绑定、收据/令牌校验、webhook/服务器通知、幂等、防重放、乱序处理、定期对账和审计日志。
4. 完整权益状态机与服务器端权益裁决；试用、续费、期末取消、失败宽限、到期 Free 降级、退款/撤销/拒付均有规则和测试。
5. 购买确认披露、清楚的取消/管理入口、退款支持/申诉、购买恢复、换机登录、账号冲突与重复订阅防护。
6. 价格按服务端/商店真实目录展示；美国/欧洲各目标国家的税务与消费者披露经核验；隐私政策、条款、收据/发票、客服渠道齐备。
7. 若上架原生商店，完成 StoreKit/Play Billing 原生集成与审核材料；若只做 PWA，移除不可用商店支付选项和暗示，明确网页订阅权益范围。
8. 上线监控与人工处置准备：支付异常、事件积压、状态不一致、退款未同步告警，财务对账和支持负责人到位。

**P0 出口标准：**每个目标平台/地区至少通过测试环境的首次购买、恢复、续订/状态通知、取消、退款、支付失败/重试、账号换机等验收；所有成功扣款最终有正确权益，所有退款/撤销最终有正确权益状态且有可审计记录；不存在模拟成功路径。

### P1：首发后尽快补齐（不应掩盖法定或平台硬要求）

- 多渠道账单门户、账单/发票下载与税务资料自助更新。
- 经过各平台规则确认的试用转付费提醒、多语言本地化与邮件/推送偏好中心。
- dunning 优化、PSP 自动卡更新、付款方式自助更新和按失败码编排重试；重试频率先遵循渠道限制，避免套用文档固定第 1/3/5/7 天方案。
- 按国家/渠道分析转化、流失、恢复、退款及拒付，建立价格实验的审批与版本审计。
- 运营后台的客服对账、补发/撤销权益和退款审批权限分离。

### P2：增长与扩展

- 暂停订阅、合规挽回方案、家庭/团队套餐；先验证商店能力和目标市场需求。
- Lifetime、离线包买断、转写消耗包、实体配件商城；按商店规则和税务分类分别建模。
- 更多 OEM 商店、支付方式和国家扩展；每增加一个渠道都独立完成账号绑定、通知、退款、对账与合规评审。
